# Update-WSUSComputerOperatingSystems — форк с событийным мониторингом

**Язык:** [English](README.md) | **Русский**

Этот форк основан на [Borgquite/Update-WSUSComputerOperatingSystems](https://github.com/Borgquite/Update-WSUSComputerOperatingSystems) и сохраняет таблицы соответствия операционных систем, сборок и редакций исходного проекта. **Событийный мониторинг и усовершенствованное журналирование разработаны в этом форке.**

В форке реализованы непрерывное отслеживание изменений `OSDescription` в WSUS через SQL Query Notifications (`SqlDependency`), автоматическое исправление названий ОС после перезаписи клиентскими агентами, восстановление SQL-соединения, установщик задания планировщика и настройка локального или сетевого каталога журналов с локальной диагностикой ошибок записи. Непрерывный мониторинг включается режимом `-AsService`; однократная проверка также доступна.

**Установка модуля PowerShell `SqlServer`, поставщика NuGet и других сторонних компонентов не требуется.** Используется `System.Data.SqlClient` из .NET Framework, доступного в Windows PowerShell 5.1.

> **Предупреждение:** программа напрямую изменяет базу данных WSUS `SUSDB`, а не использует официальный поддерживаемый Microsoft API управления WSUS. Перед внедрением создайте и проверьте резервную копию. Сначала протестируйте решение в некритичной среде. Программа распространяется без гарантий по лицензии GPL-3.0.

## Требования

- Windows Server 2019 Core или новее; Windows PowerShell 5.1 (Desktop edition).
- WSUS с Windows Internal Database (WID) или Microsoft SQL Server.
- Учётная запись для подключения к SQL с правами чтения таблиц `dbo.tbComputerTarget` и `dbo.tbComputerTargetDetail` и изменения поля `OSDescription`.
- Для `-AsService`: работающий Service Broker в `SUSDB` и разрешения на SQL Query Notifications / `SqlDependency`. Убедитесь, что учётная запись задачи (по умолчанию `SYSTEM`) может создавать необходимые подписки на SQL-уведомления.
- Загрузка дополнительных модулей PowerShell не требуется.

## Ручной запуск

Выполняйте команды на сервере WSUS из Windows PowerShell 5.1, запущенного от имени администратора:

```powershell
# Однократно проверить все компьютеры, исправить неправильные названия ОС и завершить работу.
.\Update-WSUSComputerOperatingSystems.ps1

# Проверить существующие записи, затем непрерывно отслеживать изменения.
.\Update-WSUSComputerOperatingSystems.ps1 -AsService

# Отслеживать изменения в течение 60 минут и завершить работу.
.\Update-WSUSComputerOperatingSystems.ps1 -AsService -DurationMinutes 60
```

По умолчанию `-SQLServerInstance` указывает на локальный именованный канал WID: `\\.\pipe\MICROSOFT##WID\tsql\query`. Для внешнего SQL Server:

```powershell
.\Update-WSUSComputerOperatingSystems.ps1 -SQLServerInstance 'SQLSERVER\INSTANCE' -AsService
```

Значение `-Encrypt Optional` используется по умолчанию (ADO.NET `Encrypt=False`); `-Encrypt Mandatory` включает ADO.NET `Encrypt=True` и требует доверенного сертификата сервера. Допускаются также значения `True` и `False`. Параметр `-DurationMinutes` можно использовать только вместе с `-AsService`; ноль означает отсутствие ограничения по времени. Обрабатываются известные клиентские и серверные редакции Windows, кроме исключённых LTSC. Неизвестные сборки и SKU не изменяются.

## Установка и обновление (`Update.ps1`)

**У `Update.ps1` нет параметров командной строки.** Запускайте его на сервере WSUS в **Windows PowerShell 5.1 от имени администратора**. Один и тот же файл используется для первой установки и последующих обновлений.

Источник обновлений закреплён непосредственно в начале скрипта:

```powershell
$owner = 'avmaksimov'
$repository = 'Update-WSUSComputerOperatingSystems'
$branch = 'main'
```

Обновлятор скачивает ZIP репозитория GitHub по HTTPS, сравнивает SHA-256 и показывает список файлов со статусами `INSTALL`, `REPLACE` и `UNCHANGED`. Перед заменой он подготавливает изменённые файлы рядом с оригиналами с суффиксом `.new` и проверяет их хеши. Файлы и папки, начинающиеся с точки (например, `.gitignore`, `.github`), исключаются; **посторонние локальные файлы не удаляются**. Резервных копий старых версий и файлов журналов самого обновлятора нет. Замена нескольких файлов **не является единой транзакцией**.

> **Безопасность источника:** SHA-256 используется для поиска отличий и проверки скопированных файлов, **но не подтверждает автора**. HTTPS защищает передачу, однако компрометация репозитория или изменение ветки `main` могут привести к загрузке нежелательного кода. Перед подтверждением изучайте список файлов и проверяйте изменения исполняемых скриптов; ограничивайте NTFS-права на каталог установки. Основной скрипт запускается от `SYSTEM`. Для более строгой проверки используйте заранее проверенный релиз или конкретный коммит: проверки цифровой подписи здесь нет.

### Первая установка

При первом запуске, **если задача проекта отсутствует**, обновлятор один раз спрашивает:

1. **Каталог установки** (по умолчанию текущий каталог PowerShell, если он не временный).
2. **Папку планировщика** (по умолчанию корень `\`, например `\MP\`).
3. **Каталог журналов** (по умолчанию папка установки; поддерживаются UNC-пути, например `\\server3\Документы\Отдел разработки\Scripts\Data\_Logs`).
4. **SQL Server** (по умолчанию локальный WID).

После загрузки архива и сравнения файлов появляется **одно подтверждение** изменений и создания задачи. Задача запускает `Update-WSUSComputerOperatingSystems.ps1 -AsService` от `SYSTEM` при старте Windows с задержкой 1 минуту. После регистрации задача сразу запускается. Если журнал размещён на сетевой папке, учётной записи компьютера WSUS-сервера требуются права записи и на уровне SMB, и на уровне NTFS. Подключённые сетевые диски от `SYSTEM` недоступны — используйте UNC.

### Последующие обновления

Обновлятор автоматически находит единственную существующую задачу `Update-WSUSComputerOperatingSystems` в любой папке планировщика и определяет **каталог установки по аргументу `-File` в действии задачи**. Он **больше не спрашивает** каталог файлов, папку планировщика, SQL или расположение журналов и **не пересоздаёт существующую задачу**.

Если изменился основной `.ps1` и задача работала, обновлятор остановит её, заменит файлы и запустит снова. При изменении только README или самого `Update.ps1` работающий монитор не прерывается. Если изменений нет, подтверждение не требуется. Ранее остановленная вручную задача останется остановленной.

Старые задачи без `-LogDirectory` сохраняются без изменений — основной скрипт продолжает записывать журнал в свою локальную папку. Чтобы позже изменить каталог журналов или SQL, откройте **Планировщик заданий → Свойства задачи → Действия → Изменить**, исправьте аргументы и перезапустите задачу. Для переноса задачи в другую папку планировщика используйте экспорт и импорт, проверив действие и учётную запись: обновлятор автоматически найдёт её в новом расположении.

Если обнаружено несколько подходящих задач либо одноимённая посторонняя задача, обновление прерывается вместо выбора наугад. Пользовательские настройки существующей задачи (триггеры и т. п.) сохраняются. Для удаления задачи запустите `Uninstall.ps1` от администратора. Он удалит только задачу после подтверждения; локальные скрипты и журналы сохранятся.

### Удаление (`Uninstall.ps1`)

Запустите на сервере WSUS в Windows PowerShell 5.1 от имени администратора:

```powershell
.\Uninstall.ps1
```

Скрипт **не принимает параметров**. Он находит задачу проекта в любой папке планировщика, проверяет, что она запускает наш монитор, и запрашивает одно подтверждение. При нескольких одноимённых задачах или совпадении имени с посторонней задачей удаление не выполняется. Работающая задача предварительно останавливается. **Удаляется только само задание**; папка планировщика, скрипты, документация и журналы сохраняются. При следующем запуске `Update.ps1` снова предложит первоначальную настройку задания, а уже имеющиеся неизменённые файлы повторно не заменит.

### Скачать и запустить

**Одна команда PowerShell, записанная в несколько строк**, скачивает **только `Update.ps1`** во временный файл с уникальным именем в `%TEMP%`, запускает без параметров, затем удаляет копию. При повторном обновлении расположение файлов определяется из планировщика, а не из временного каталога. Скопируйте и вставьте весь блок в PowerShell:

```powershell
& {
    $f = Join-Path $env:TEMP ("WSUS-Update-$([guid]::NewGuid().ToString('N')).ps1")
    $url = 'https://raw.githubusercontent.com/avmaksimov/Update-WSUSComputerOperatingSystems/main/Update.ps1'
    try {
        Invoke-WebRequest -UseBasicParsing $url -OutFile $f -ErrorAction Stop
        & $f
    }
    finally {
        Remove-Item -LiteralPath $f -Force -ErrorAction SilentlyContinue
    }
}
```

Либо запустите установленный файл непосредственно:

```powershell
& 'C:\Scripts\WSUS\Update.ps1'
```

Для другого репозитория измените константы `$owner`, `$repository`, `$branch` в самом скрипте; параметров URL и внешнего конфигурационного файла нет. Ранее установленные файлы со старыми именами автоматически не удаляются.

## Как работает отслеживание событий

1. Загружается каталог соответствий ОС (актуальные комбинации операционная система / сборка / SKU).
2. В режиме однократного запуска считываются все строки `tbComputerTargetDetail` и исправляются только ошибочные названия.
3. В режиме `-AsService` подписка `SqlDependency` регистрируется **до** начальной сверки, чтобы не пропустить одновременные изменения, вносимые WSUS.
4. При SQL-уведомлении следующая подписка регистрируется до обработки изменений. Старый и новый снимки таблицы сравниваются по числовому `TargetID`; перед записью проверяются поля ОС, сборки и SKU.
5. Собственные SQL-запросы `UPDATE` также могут вызывать уведомления. При следующем проходе повторный `UPDATE` **не выполняется**, если название уже соответствует каталогу.
6. При ошибке SQL текущий обработчик останавливается, выполняется пауза 15 секунд, затем переподключение и повторная проверка всей таблицы.

Триггеры в `SUSDB` не создаются; скрипт также не удаляет вручную объекты Service Broker, созданные `SqlDependency`. Мьютекс не используется. Следует держать только один экземпляр постоянного обработчика благодаря настройке планировщика `MultipleInstances=IgnoreNew`. Если сохранилась старая периодическая задача, отключите её, чтобы избежать лишних параллельных изменений.

## Журналирование

Основной скрипт записывает журнал в каталог, выбранный при **первой установке**, под именем `Update-WSUSComputerOperatingSystems.log`. По умолчанию используется папка установки; допускается UNC-путь. Папка задания в планировщике (например, `\MP\`) не влияет на каталог журнала.

- **Первая установка:** `Update.ps1` один раз спрашивает каталог журналов. Нажатие Enter выбирает папку установки; указанный путь сохраняется в аргументе `-LogDirectory` создаваемого задания.
- **Последующие обновления:** `Update.ps1` читает настройки существующего задания, **не задаёт повторных вопросов** о журнале и не перезаписывает действие задания. Старая задача без `-LogDirectory` также остаётся без изменений и продолжает писать журнал в свою локальную папку.
- **Изменение пути впоследствии:** откройте **Планировщик заданий → Свойства задачи → Действия → Изменить** и измените путь внутри `-LogDirectory "..."` (сохраните двойные кавычки). Остановите и снова запустите задачу, чтобы работающий монитор начал использовать новый путь. Сам `Update.ps1` параметров командной строки для изменения настроек не принимает.

Для сетевой папки используйте **UNC-путь**, а не подключённый пользователем диск вроде `M:`. Задача работает от `NT AUTHORITY\SYSTEM`; при обращении к SMB-серверу обычно используется доменная учётная запись компьютера (например, `BS\SERVER1$`). Для неё необходимо предоставить права на запись как в разрешениях сетевого ресурса, так и NTFS. Обновлятор напоминает об этом, но не изменяет права доступа.

Основной журнал содержит обычные записи уровней `INFO`, `WARNING` и `ERROR` **только в выбранном каталоге**. Если он отличается от папки скрипта, предупреждения и ошибки также записываются в локальный диагностический файл рядом с основным PS1: `Update-WSUSComputerOperatingSystems_errors.log`. Если запись в выбранную папку невозможна (например, SMB-ресурс временно недоступен), ошибка и несохранённая запись сохраняются в локальном диагностическом журнале. Мониторинг продолжает работу; следующие записи снова отправляются в выбранный каталог, однако записи, потерянные при сбое, автоматически туда не переносятся. Если основной журнал локальный и запись в него не удалась, также используется локальный файл ошибок.

Для каждой строки используется местное время сервера в формате `dd.MM.yyyy HH:mm:ss.fff [LEVEL] Message`, где возможны уровни `INFO`, `WARNING` и `ERROR`. Пример:

```text
24.10.2026 21:57:34.345 [INFO] Catalog loaded: 979 combinations. Mode=SERVICE.
24.10.2026 21:57:34.678 [ERROR] SQL/listener error: ...; reconnecting in 15 seconds.
```

При запуске и после восстановления SQL-подключения полная проверка записывает одну сводку `Reconciliation: checked=...; wrong=...; updated=...` без отдельных строк `UPDATED INITIAL` для каждого компьютера. При обычной обработке событий записываются только реальные исправления (`UPDATED CHANGED ...`), предупреждения и ошибки. Повторяющаяся сводка `Affected=...` после каждого уведомления больше не выводится.

Основной скрипт работает **только в режиме добавления записей**: он не ротирует, не обрезает и не удаляет журналы. При необходимости настройте срок хранения или ротацию отдельно. При постоянной ошибке подключения сообщения могут появляться каждые 15 секунд. Журналируются загрузка каталога, реальные исправления, ошибки SQL и переподключения; уведомления, не требующие изменений, не записываются. Файлы журналов создаются при запуске основного скрипта, а не установщика.

Для просмотра основного журнала в реальном времени (исправьте путь в соответствии с заданием планировщика):

```powershell
Get-Content 'C:\Scripts\Update-WSUSComputerOperatingSystems\Update-WSUSComputerOperatingSystems.log' -Tail 30 -Wait
```

## Проверка перед использованием в рабочей среде

Используйте актуальную резервную копию `SUSDB`. На целевом сервере проверьте следующее:

1. Запустите скрипт без `-AsService`, посмотрите журнал и консоль WSUS. Повторный запуск не должен приводить к изменениям.
2. Запустите `-AsService -DurationMinutes 60`, дождитесь очередного отчёта от клиента WSUS и убедитесь, что перезаписанные названия ОС исправляются.
3. После установки проверьте автоматически запущенную задачу от `SYSTEM`, включая доступ к WID и `SqlDependency`.
4. Во время обслуживания перезапустите службу WID и убедитесь, что обработчик переподключается и повторно проверяет все записи.
5. Проверьте Ctrl+C и принудительное завершение с последующим немедленным запуском.
6. Убедитесь, что прежняя задача `WSUS Update Operating Systems`, если она есть, осталась без изменений; при необходимости отключите её отдельно.

### Автономная проверка каталога ОС

Перед запуском основного скрипта с доступом к `SUSDB` можно выполнить:

```powershell
.\tests\Test-WSUSCatalog.ps1
```

Выводится текущий размер каталога (без жёстко заданного значения 1094), проверяются характерные соответствия Windows 10/11/Server/Azure Stack HCI, а функции SQL и журналирования заменяются заглушками для тестов начальной сверки, уведомлений без изменений, исправления названия после перезаписи агентом WSUS, смены сборки и пропуска параллельных `UPDATE`. ## Дополнительные проверки в рабочей среде

- Проверяйте работу установщика и задания именно **от SYSTEM**, а не только из интерактивного PowerShell с повышенными правами. После ручного запуска задания проверьте `Update-WSUSComputerOperatingSystems.log` в выбранной папке, а если были ошибки записи — `Update-WSUSComputerOperatingSystems_errors.log` рядом со скриптом.
- Должна работать только одна постоянная задача с `-AsService`. Команда `Get-ScheduledTask -TaskName 'WSUS*'` помогает найти старые задания; перед отключением внимательно проверьте их.
- Тестовый запуск `-AsService` на 60 минут подтверждает старт и ожидание событий; дополнительно проверьте фактическое исправление названия после перезаписи `OSDescription` клиентом.
- Проверьте, что SQL-уведомления Service Broker в базе `SUSDB` остаются включёнными. Скрипт рассчитывает на это и самостоятельно их не включает.
- При ошибке подключения к SQL обработчик повторяет попытку через 15 секунд; постоянные ошибки отражаются в журнале, но не вызывают ошибку задания в планировщике, поскольку процесс продолжает работать.
- SQL-записи напрямую изменяют `SUSDB`, а не работают через поддерживаемый API WSUS. Храните проверенную резервную копию и проверяйте работу после обновлений WSUS.
