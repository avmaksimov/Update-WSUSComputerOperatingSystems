# Update-WSUSComputerOperatingSystems — форк с событийным мониторингом

**Язык:** [English](README.md) | **Русский**

Проект основан на [Borgquite/Update-WSUSComputerOperatingSystems](https://github.com/Borgquite/Update-WSUSComputerOperatingSystems) и сохраняет таблицы соответствия операционных систем, сборок и редакций из оригинала. Дополнительно реализован необязательный событийный режим, который исправляет значения `OSDescription` в Windows Server Update Services (WSUS), когда клиентские агенты перезаписывают их.

Механизм отслеживания событий основан на протестированном прототипе `Watch-WSUSOS-AutoFix-v1.1.ps1`. **Установка модуля PowerShell `SqlServer`, поставщика NuGet и других сторонних компонентов не требуется.** Используется `System.Data.SqlClient` из .NET Framework, доступного в Windows PowerShell 5.1.

> **Предупреждение:** программа напрямую изменяет базу данных WSUS `SUSDB`, а не использует официальный поддерживаемый Microsoft API управления WSUS. Перед внедрением создайте и проверьте резервную копию. Сначала протестируйте решение в некритичной среде. Программа распространяется без гарантий по лицензии GPL-3.0.

## Требования

- Windows Server 2019 Core или новее; Windows PowerShell 5.1 (Desktop edition).
- WSUS с Windows Internal Database (WID) или Microsoft SQL Server.
- Учётная запись для подключения к SQL с правами чтения таблиц `dbo.tbComputerTarget` и `dbo.tbComputerTargetDetail` и изменения поля `OSDescription`.
- Для `-AsService`: работающий Service Broker в `SUSDB` и разрешения на SQL Query Notifications / `SqlDependency`. Убедитесь, что учётная запись задачи (по умолчанию `SYSTEM`) может создавать необходимые подписки на SQL-уведомления.
- Загрузка дополнительных модулей PowerShell не требуется.

## Ручной запуск

Выполняйте команды на сервере WSUS из Windows PowerShell 5.1, запущенного от имени администратора:

```powershell
# Однократно проверить все компьютеры, исправить неправильные названия ОС и завершить работу.
.\Update-WSUSComputerOperatingSystems.ps1

# Проверить существующие записи, затем непрерывно отслеживать изменения.
.\Update-WSUSComputerOperatingSystems.ps1 -AsService

# Отслеживать изменения в течение 60 минут и завершить работу.
.\Update-WSUSComputerOperatingSystems.ps1 -AsService -DurationMinutes 60
```

По умолчанию `-SQLServerInstance` указывает на локальный именованный канал WID: `\\.\pipe\MICROSOFT##WID\tsql\query`. Для внешнего SQL Server:

```powershell
.\Update-WSUSComputerOperatingSystems.ps1 -SQLServerInstance 'SQLSERVER\INSTANCE' -AsService
```

Значение `-Encrypt Optional` используется по умолчанию (ADO.NET `Encrypt=False`); `-Encrypt Mandatory` включает ADO.NET `Encrypt=True` и требует доверенного сертификата сервера. Допускаются также значения `True` и `False`. Параметр `-DurationMinutes` можно использовать только вместе с `-AsService`; ноль означает отсутствие ограничения по времени. Обрабатываются известные клиентские и серверные редакции Windows, кроме исключённых LTSC. Неизвестные сборки и SKU не изменяются.

## Установка (задание планировщика)

Запускайте установщик **на сервере WSUS** из **Windows PowerShell 5.1 от имени администратора**. Создаваемое задание выполняет основной скрипт **непосредственно из каталога установки**: копирования в `Program Files` нет. Если `-InstallPath` не задан, установщик ищет основной PS1 **рядом с собственным файлом** (`$PSScriptRoot`), а не в текущем каталоге PowerShell (`$PWD`). Для установки достаточно файла установщика. Если основного скрипта нет, он будет загружен. Если файл уже существует, появится вопрос `Download the latest version? [Y/n]` (по умолчанию **Yes**).

> **Источник на GitHub:** установщик и команды быстрой установки загружают файлы из [`avmaksimov/Update-WSUSComputerOperatingSystems`](https://github.com/avmaksimov/Update-WSUSComputerOperatingSystems), ветка `main`. **Перед применением команд загрузки убедитесь, что в этой ветке уже опубликованы обновлённые установщик и основной скрипт.** Локальные изменения не появляются на GitHub автоматически. Чтобы проверить отредактированный локальный скрипт, ответьте **No** на `Download the latest version?` либо укажите другой доверенный URL через `-MainScriptUrl`. Не переключайте URL загрузки на оригинальный репозиторий Borgquite, пока в нём нет необходимых изменений для событийного режима.

### Быстрая установка (скачивание и запуск Install)

Следующие однострочные команды загружают **только установщик** во временный файл с уникальным именем в `%TEMP%`, запускают его и удаляют временную копию. Затем установщик загружает или обновляет основной скрипт в выбранном *постоянном* каталоге и регистрирует задачу планировщика. Существующий основной скрипт не перезаписывается без соответствующего запроса. Перед выполнением кода из интернета рекомендуется ознакомиться с загруженным установщиком.

**А. Установка в текущий каталог.** Сначала перейдите в нужную постоянную папку (`Set-Location` или `cd`), затем выполните команду. Она явно передаёт эту папку через `-InstallPath`, поскольку сам скачанный установщик находится в `%TEMP%`:

```powershell
$f=Join-Path $env:TEMP ("WSUS-Install-$([guid]::NewGuid().ToString('N')).ps1"); try { Invoke-WebRequest -UseBasicParsing 'https://raw.githubusercontent.com/avmaksimov/Update-WSUSComputerOperatingSystems/main/Install-WSUSComputerOperatingSystems.ps1' -OutFile $f -ErrorAction Stop; & $f -InstallPath (Get-Location).ProviderPath } finally { Remove-Item -LiteralPath $f -Force -ErrorAction SilentlyContinue }
```

**Б. Установка в явно заданный каталог.** Замените `C:\Scripts\WSUS` на нужную постоянную папку. Предварительно переходить в неё не требуется:

```powershell
$f=Join-Path $env:TEMP ("WSUS-Install-$([guid]::NewGuid().ToString('N')).ps1"); try { Invoke-WebRequest -UseBasicParsing 'https://raw.githubusercontent.com/avmaksimov/Update-WSUSComputerOperatingSystems/main/Install-WSUSComputerOperatingSystems.ps1' -OutFile $f -ErrorAction Stop; & $f -InstallPath 'C:\Scripts\WSUS' } finally { Remove-Item -LiteralPath $f -Force -ErrorAction SilentlyContinue }
```

URL останется действительным, пока сохраняются название ветки и расположение файла в репозитории. При их изменении ссылку необходимо обновить. Команды скачивают текущую версию из ветки, а не закреплённый релиз; для воспроизводимой установки используйте в URL неизменяемый тег релиза или хеш коммита.

### Ручная установка (два варианта)

Скачайте `Install-WSUSComputerOperatingSystems.ps1` из форка (либо распакуйте ZIP репозитория). Если установщик находится в целевом постоянном каталоге, его можно запустить из любого места: он найдёт основной скрипт рядом с собой. Если установщик лежит во временной папке, необходимо выбрать постоянное расположение — ответом на запрос либо через `-InstallPath`. Текущий каталог вызывающей консоли сам по себе на выбор расположения не влияет.

**А. Установка рядом с установщиком (по умолчанию):**

```powershell
# Установщик расположен в постоянной папке; текущий каталог консоли не важен.
& 'C:\Scripts\WSUS\Install-WSUSComputerOperatingSystems.ps1'
```

Если основной скрипт **уже находится рядом с установщиком**, вопрос о каталоге установки пропускается. Если его нет, установщик предложит собственную папку по умолчанию — нажмите Enter для подтверждения (если сам установщик не находится во временной папке).

**Б. Установка в явно заданный каталог:**

```powershell
& 'C:\Temp\WSUS\Install-WSUSComputerOperatingSystems.ps1' -InstallPath 'D:\Scripts\WSUS'
```

`-InstallPath` позволяет не отвечать на вопрос о папке, если указан корректный постоянный путь. `C:\Temp\WSUS` — только **пример расположения скачанного установщика**, а не каталог для постоянно работающего скрипта.

### Вопросы установщика и параметры задачи

- Если в целевой папке нет основного PS1, он загружается автоматически. Если уже есть — предлагается скачать последнюю версию (по умолчанию **Yes**); ответ **No** оставляет существующий файл.
- Если `-InstallPath` не указан, установщик ищет основной PS1 рядом с собой (`$PSScriptRoot`). Если он отсутствует, задаётся вопрос о целевой папке с **каталогом установщика** в качестве значения по умолчанию.
- При выборе временного каталога (`%TEMP%`, `%TMP%`, `C:\Temp` и т. п.) требуется указать другой, постоянный путь. Пустой ответ недопустим, если предложенная по умолчанию папка временная. Сам файл **Install** может запускаться из временного каталога.
- Установщик автоматически ищет существующую задачу проекта во всех папках планировщика. Если найдена одна — сохраняется её папка; если подходящих задач нет — используется корень (`\`). При нескольких совпадениях нужно явно указать `-TaskPath`. Посторонние задачи с тем же именем не изменяются.
- **Каталог журналов:** при новой установке установщик спрашивает, куда записывать `Update-WSUSComputerOperatingSystems.log`, предлагая постоянный каталог основного скрипта. **Enter** или пустое значение означают этот каталог; установщик сообщает о выборе значения по умолчанию. Поддерживаются абсолютные локальные пути и сетевые UNC-пути.
- **Переход со старой задачи без `-LogDirectory`:** каталог запрашивается **один раз**; по умолчанию предлагается каталог основного скрипта. После подтверждения установщик записывает `-LogDirectory "..."` в действие задания.
- **Следующие обновления:** если в задаче уже имеется `-LogDirectory`, установщик считывает и сохраняет его **без дополнительного вопроса**, показывая путь в `Installation summary`. Явно переданный установщику `-LogDirectory` имеет приоритет (пустая строка возвращает каталог основного скрипта).
- Показывается сводка установки и запрашивается подтверждение. Существующая задача обновляется только после явного согласия. Если подходящей задачи проекта нет, но обнаружена посторонняя задача с тем же именем, установка останавливается до явного выбора `-TaskPath`. О других одноимённых задачах выводится сообщение, но они не изменяются.
- Создаётся или обновляется только задача проекта **`Update-WSUSComputerOperatingSystems`**. Существующая задача `WSUS Update Operating Systems`, если она есть, не заменяется.
- Основной скрипт скачивается во временную промежуточную папку, проверяется синтаксис PowerShell и поддержка `-AsService` и `-LogDirectory`. Замена выполняется только после подтверждения. Работающая задача останавливается перед перенастройкой и **запускается снова после неё**. Новая задача **запускается сразу** после регистрации (помимо триггера при старте сервера).
- Задача регистрируется от `SYSTEM`, с задержкой запуска 1 минута после старта Windows, без ограничения времени выполнения и с перезапуском при ошибке. Действие задачи запускает `Update-WSUSComputerOperatingSystems.ps1 -AsService -LogDirectory "..."` из выбранной постоянной папки.
- Установщик не копирует собственный файл в каталог установки. Удаление установки убирает **только задачу планировщика**, не затрагивая файлы и журналы.

Для задания другой папки планировщика или параметров SQL без дополнительных вопросов:

```powershell
.\Install-WSUSComputerOperatingSystems.ps1 -InstallPath 'C:\Scripts\WSUS' -TaskPath '\MP'
.\Install-WSUSComputerOperatingSystems.ps1 -InstallPath 'C:\Scripts\WSUS' -TaskPath '\MP' -SQLServerInstance 'SQLSERVER\INSTANCE' -Encrypt Mandatory
```

После успешной регистрации установщик запрашивает немедленный запуск задачи. Проверьте по журналу, что процесс запускается и получает доступ к SQL под `SYSTEM`. Для ручного повторного запуска:

```powershell
Start-ScheduledTask -TaskPath '\MP' -TaskName 'Update-WSUSComputerOperatingSystems'
```

Для удаления задачи (файлы скриптов остаются на месте) установщик автоматически определяет её папку, если найдена ровно одна задача проекта:

```powershell
.\Install-WSUSComputerOperatingSystems.ps1 -Uninstall
```

Указывайте `-TaskPath '\MP'` только при наличии нескольких задач проекта или необходимости выбрать конкретную папку.

**Безопасность:** установщик необходимо запускать с повышенными правами, поскольку он регистрирует задачу под `SYSTEM`. Ограничьте права на изменение файлов в постоянном каталоге установки: любой пользователь, способный подменить основной PS1, сможет запустить свой код с правами `SYSTEM`. Проверяйте удалённый код и источник загрузки. Если основной PS1 уже есть и вы отказались от обновления, скрипты не скачиваются.

## Как работает отслеживание событий

1. Загружается каталог соответствий ОС (актуальные комбинации операционная система / сборка / SKU).
2. В режиме однократного запуска считываются все строки `tbComputerTargetDetail` и исправляются только ошибочные названия.
3. В режиме `-AsService` подписка `SqlDependency` регистрируется **до** начальной сверки, чтобы не пропустить одновременные изменения, вносимые WSUS.
4. При SQL-уведомлении следующая подписка регистрируется до обработки изменений. Старый и новый снимки таблицы сравниваются по числовому `TargetID`; перед записью проверяются поля ОС, сборки и SKU.
5. Собственные SQL-запросы `UPDATE` также могут вызывать уведомления. При следующем проходе повторный `UPDATE` **не выполняется**, если название уже соответствует каталогу.
6. При ошибке SQL текущий обработчик останавливается, выполняется пауза 15 секунд, затем переподключение и повторная проверка всей таблицы.

Триггеры в `SUSDB` не создаются; скрипт также не удаляет вручную объекты Service Broker, созданные `SqlDependency`. Мьютекс не используется. Следует держать только один экземпляр постоянного обработчика благодаря настройке планировщика `MultipleInstances=IgnoreNew`. Если сохранилась старая периодическая задача, отключите её, чтобы избежать лишних параллельных изменений.

## Журналирование

Основной скрипт записывает обычный журнал в каталог, указанный параметром `-LogDirectory`, под именем `Update-WSUSComputerOperatingSystems.log`. Если параметр отсутствует или передана пустая строка, используется каталог основного скрипта (`$PSScriptRoot`). Папка задания в планировщике (например, `\MP\`) не влияет на путь к журналу.

- **Новая установка:** установщик спрашивает каталог журнала, предлагая по умолчанию папку основного скрипта. Enter или пустой ответ выбирают эту папку; выводится пояснение.
- **Первое обновление старой задачи:** если в действии задания нет `-LogDirectory`, установщик **один раз** задаёт вопрос и предлагает ту же папку по умолчанию. Выбранный путь сохраняется в обновлённом действии задачи.
- **Обычные обновления:** установщик без вопросов читает `-LogDirectory` из существующего задания и показывает сохранённый путь в `Installation summary`.
- **Явное изменение:** передайте установщику `-LogDirectory` для смены папки либо `-LogDirectory ''`, чтобы вернуться к каталогу основного скрипта.

Например, чтобы указать либо впоследствии изменить папку повторным запуском установщика:

```powershell
.\Install-WSUSComputerOperatingSystems.ps1 -LogDirectory '\\fileserver\share\WSUS\_Logs'
```

Также можно **изменить путь непосредственно в планировщике Windows**: на сервере WSUS откройте `taskschd.msc`, перейдите в **Библиотека планировщика заданий → MP**, затем откройте **Update-WSUSComputerOperatingSystems → Свойства → Действия → Изменить**. Исправьте только путь внутри аргумента `-LogDirectory "..."` (сохраните двойные кавычки). Сохраните задачу. Чтобы работающий процесс начал использовать новый путь, **остановите и снова запустите задачу**. При последующих обновлениях установщик прочитает путь из планировщика. Вариант с установщиком предпочтительнее, если нужны его проверка параметров и отображение пути в сводке установки.

Для сетевой папки используйте **UNC-путь**, а не пользовательский сетевой диск вроде `M:`. Задача работает от `NT AUTHORITY\SYSTEM`; при обращении к SMB-серверу обычно используется доменная учётная запись компьютера (например, `BS\SERVER1$`). Для неё необходимо предоставить права на запись как в разрешениях сетевого ресурса, так и NTFS. Установщик напоминает об этом, но не изменяет права доступа.

Основной журнал содержит обычные записи уровней `INFO`, `WARNING` и `ERROR` **только в выбранном каталоге**. Если он отличается от папки скрипта, предупреждения и ошибки также записываются в локальный диагностический файл рядом с основным PS1: `Update-WSUSComputerOperatingSystems_errors.log`. Если запись в выбранную папку невозможна (например, SMB-ресурс временно недоступен), ошибка и несохранённая запись сохраняются в локальном диагностическом журнале. Мониторинг продолжает работу; следующие записи снова отправляются в выбранный каталог, однако записи, потерянные при сбое, автоматически туда не переносятся. Если основной журнал локальный и запись в него не удалась, также используется локальный файл ошибок.

Для каждой строки используется местное время сервера в формате `dd.MM.yyyy HH:mm:ss.fff [LEVEL] Message`, где возможны уровни `INFO`, `WARNING` и `ERROR`. Пример:

```text
24.10.2026 21:57:34.345 [INFO] Catalog loaded: 979 combinations. Mode=SERVICE.
24.10.2026 21:57:34.678 [ERROR] SQL/listener error: ...; reconnecting in 15 seconds.
```

Основной скрипт работает **только в режиме добавления записей**: он не ротирует, не обрезает и не удаляет журналы. При необходимости настройте срок хранения или ротацию отдельно. При постоянной ошибке подключения сообщения могут появляться каждые 15 секунд. Журналируются загрузка каталога, реальные исправления, ошибки SQL и переподключения; уведомления, не требующие изменений, не записываются. Файлы журналов создаются при запуске основного скрипта, а не установщика.

Для просмотра основного журнала в реальном времени (исправьте путь в соответствии с заданием планировщика):

```powershell
Get-Content 'C:\Scripts\Update-WSUSComputerOperatingSystems\Update-WSUSComputerOperatingSystems.log' -Tail 30 -Wait
```

## Проверка перед использованием в рабочей среде

Используйте актуальную резервную копию `SUSDB`. На целевом сервере проверьте следующее:

1. Запустите скрипт без `-AsService`, посмотрите журнал и консоль WSUS. Повторный запуск не должен приводить к изменениям.
2. Запустите `-AsService -DurationMinutes 60`, дождитесь очередного отчёта от клиента WSUS и убедитесь, что перезаписанные названия ОС исправляются.
3. После установки проверьте автоматически запущенную задачу от `SYSTEM`, включая доступ к WID и `SqlDependency`.
4. Во время обслуживания перезапустите службу WID и убедитесь, что обработчик переподключается и повторно проверяет все записи.
5. Проверьте Ctrl+C и принудительное завершение с последующим немедленным запуском.
6. Убедитесь, что прежняя задача `WSUS Update Operating Systems`, если она есть, осталась без изменений; при необходимости отключите её отдельно.

### Автономная проверка каталога ОС

Перед запуском основного скрипта с доступом к `SUSDB` можно выполнить:

```powershell
.\tests\Test-WSUSCatalog.ps1
```

Проверка разбирает текст скрипта и выполняет **только** встроенные определения каталога ОС и функции; никаких SQL-запросов на чтение или запись не выполняется. Выводится текущий размер каталога (без жёстко заданного значения 1094), проверяются характерные соответствия Windows 10/11/Server/Azure Stack HCI, а функции SQL и журналирования заменяются заглушками для тестов начальной сверки, уведомлений без изменений, исправления названия после перезаписи агентом WSUS, смены сборки и пропуска параллельных `UPDATE`. Также проверяются важные защитные условия SQL. **Основной скрипт не запускается.** Для теста не требуется WSUS или подключение к `SUSDB`.

## Дополнительные проверки в рабочей среде

- **Основной скрипт сохраняет последнюю протестированную структуру каталога ОС и логику SQL-событий и обновлений; в этом комплекте изменено только журналирование.** В старом черновом ZIP другая организация каталога; не заменяйте текущий скрипт тем вариантом.
- Проверяйте работу установщика и задания именно **от SYSTEM**, а не только из интерактивного PowerShell с повышенными правами. После ручного запуска задания проверьте `Update-WSUSComputerOperatingSystems.log` в выбранной папке, а если были ошибки записи — `Update-WSUSComputerOperatingSystems_errors.log` рядом со скриптом.
- Должна работать только одна постоянная задача с `-AsService`. Команда `Get-ScheduledTask -TaskName 'WSUS*'` помогает найти старые задания; перед отключением внимательно проверьте их.
- Тестовый запуск `-AsService` на 60 минут подтверждает старт и ожидание событий; дополнительно проверьте фактическое исправление названия после перезаписи `OSDescription` клиентом.
- Проверьте, что SQL-уведомления Service Broker в базе `SUSDB` остаются включёнными. Скрипт рассчитывает на это и самостоятельно их не включает.
- При ошибке подключения к SQL обработчик повторяет попытку через 15 секунд; постоянные ошибки отражаются в журнале, но не вызывают ошибку задания в планировщике, поскольку процесс продолжает работать.
- SQL-записи напрямую изменяют `SUSDB`, а не работают через поддерживаемый API WSUS. Храните проверенную резервную копию и проверяйте работу после обновлений WSUS.
